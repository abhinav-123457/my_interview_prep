01

Transformers

Self-attention

For each token, compute three vectors: Query (Q), Key (K), Value (V).

Query

"What am I looking for?"

Key

"What do I contain?"

Value

"What do I contribute?"

Every token's Q is compared against every token's K to produce attention weights, which take a weighted sum of the V vectors.

Scaled dot-product attention

Attention(Q,K,V) = softmax( (Q · Kᵀ) / √dk ) · V
  • Q · Kᵀ — similarity between every query and every key
  • Why divide by √dk? With large dimensions the dot products grow, pushing softmax into regions with vanishing gradients. Scaling keeps training stable.
  • softmax — turns scores into weights summing to 1

Multi-head attention

Run attention h times in parallel with different learned projections, then concatenate. Each head specialises — one tracks syntax, another long-range references, another local context. More expressive than one large head.

Positional encoding

Attention is permutation-invariant — without position information, "dog bites man" equals "man bites dog."

  • Sinusoidal — fixed sine/cosine patterns (original paper)
  • Learned — trained position embeddings
  • RoPE (Rotary) — rotates Q/K by position; used in Llama, and enables context extension beyond the trained length. Current standard.
  • ALiBi — biases attention by distance

Masking

  • Causal / look-ahead mask — in decoders, token i only sees tokens ≤ i. This makes generation autoregressive and prevents the model seeing the future during training.
  • Padding mask — ignore padding tokens in batched sequences.

The transformer block

x → LayerNorm → Multi-Head Attention → + residual
  → LayerNorm → Feed-Forward Network  → + residual
  • Layer normalization — normalises across features, stabilises training. Pre-LN (norm before the sublayer) is now standard over the original Post-LN. Many modern models use RMSNorm, which is cheaper.
  • Feed-forward network — two linear layers with a non-linearity, applied per position. Usually expands to 4× model dimension and back. Holds most of the model's parameters.
  • Residual connections — the + x skip lets gradients flow through very deep stacks.

The three architectures

TypeAttentionExamplesBest for
Encoder-onlyBidirectionalBERT, RoBERTa, DistilBERTUnderstanding: classification, NER, embeddings, reranking
Decoder-onlyCausal, left-to-rightGPT, Llama, MistralGeneration. All modern LLMs.
Encoder-decoderBothT5, BARTSeq2seq: translation, summarisation
  • BERT — trained with Masked Language Modelling (predict hidden words) plus next-sentence prediction.
  • RoBERTa — BERT trained better: more data, longer, no NSP, dynamic masking.
  • DistilBERT — distilled: ~40% smaller, ~60% faster, ~97% of performance.
  • Decoder / Causal LM — trained on next-token prediction. Autoregressive means generate one token, append, repeat.
  • T5 — every task framed as text-to-text.
Why this matters downstream

A cross-encoder reranker is an encoder model: it reads query and document together, bidirectionally. That's why it scores better than a bi-encoder — and why it's too slow to run over a whole corpus.

02

Context length, and why it isn't n-grams

N-grams — the pre-neural approach

An n-gram model predicts the next word using only the previous n−1 words, by counting frequencies in a corpus.

  • Bigram (n=2): P(next | 1 previous word). "New" → "York" is frequent, so predict "York."
  • Trigram (n=3): P(next | 2 previous words).

Three fatal flaws

  1. Fixed, tiny window. A 5-gram sees 4 words. It cannot link a noun at the start of a paragraph to a pronoun at the end.
  2. Combinatorial explosion. A 50,000-word vocabulary gives 50,000³ = 125 trillion possible trigrams. Most never occur — the sparsity problem — forcing smoothing and backoff.
  3. No notion of meaning. "cat" and "kitten" are unrelated symbols with no shared representation.

How context actually works in a transformer

  • Every token becomes an embedding — a dense vector carrying meaning.
  • Self-attention lets every token look at every other token in the window simultaneously, learning how much to weight each one. Token 4,000 can attend directly to token 1.
  • Context length = how many tokens can be attended over at once. Bounded by architecture and compute, not by an n-gram order.
  • The real limit is cost: attention is O(n²). Double the context, quadruple compute and memory.
  • Positional encoding supplies order, since attention alone is order-blind.
In one sentence

Context length comes from self-attention — every token attends to every other token in the window, so there is no fixed n-word lookback. The constraint is that attention scales quadratically with sequence length, which is why long context is expensive.

04

Fine-tuning & PEFT

Rule of thumb: RAG for facts, fine-tuning for behaviour, format and domain style.

SFT

Supervised Fine-Tuning — train on labelled input → output pairs. The standard first step for adapting a base model to a task or an instruction-following format.

PEFT — parameter-efficient fine-tuning

Full fine-tuning of a large model needs enormous GPU memory. PEFT freezes most weights and trains a small number of new parameters instead.

LoRA — the dominant method

Freeze weight matrix W; learn two small matrices A and B where ΔW ≈ B·A, with rank r far smaller than the full dimension. Trains roughly 0.1–1% of parameters.

  • r — rank / capacity (8, 16, 32, 64)
  • alpha — scaling factor
  • Target modules — usually attention Q/K/V/O

Adapters are a few MB, so many task-specific adapters can share one base model — and LoRA can be merged into the base weights, adding zero inference latency.

QLoRA

LoRA on top of a 4-bit quantized base model. Makes fine-tuning large models possible on a single consumer GPU. Introduced NF4 quantization, double quantization and paged optimizers.

Adapters

Small bottleneck layers inserted between transformer layers. Predates LoRA and adds inference latency, because it can't be merged into the base weights.

Prefix & prompt tuning

Prefix: trainable vectors prepended to keys and values at every layer. Prompt: lighter still — soft prompt embeddings at the input layer only. Effective mainly at large scale.

BitFit

Train only the bias terms. Extremely few parameters, and surprisingly competitive on some tasks.

Side tuning

Train a separate small side network whose output is combined with the frozen base model.

In practice

LoRA or QLoRA in almost every case — good quality, tiny adapters, mergeable at inference. The others are largely historical or research interest now.

Preference alignment

  • RLHF — train a reward model on human preference comparisons, then optimise the LLM against it with RL (PPO). Powerful, complex, unstable.
  • DPO — skips the reward model and RL loop entirely, optimising directly on preference pairs with a classification-style loss. Simpler, more stable, now widely preferred.
  • Also: KTO, ORPO, RLAIF (AI feedback rather than human).

Tokenization & dataset preparation

  • BPE (Byte-Pair Encoding) — start from characters, iteratively merge the most frequent pairs. Used by GPT.
  • WordPiece (BERT) and SentencePiece / Unigram (language-agnostic, no pre-tokenization required).
  • Why subwords? Handles unseen words, keeps vocabulary manageable, works across languages.
  • Dataset prep: deduplicate, quality-filter, format into the model's chat template, mask prompt tokens so loss is computed only on the response, handle truncation, hold out a validation split.
Underrated

Dataset correction usually beats model selection. Mislabelled or inconsistent data caps performance no matter which architecture sits on top of it.

Training mechanics & distributed training

TermWhat it does
Mixed precision (AMP)Compute in FP16/BF16 for speed and memory while keeping an FP32 master copy. BF16 has wider range and is more stable. Uses loss scaling so small gradients don't underflow.
Gradient accumulationCan't fit batch size 32? Run 8 micro-batches of 4, accumulate gradients, step once. Simulates a large batch on small hardware.
LR schedulingWarmup (start tiny, ramp up — prevents early instability) then decay (cosine or linear). Nearly all LLM training uses warmup plus cosine decay.
Weight decayL2-style regularisation shrinking weights toward zero to reduce overfitting. AdamW decouples it from the gradient update — that's the "W".
Gradient checkpointingRecompute activations during the backward pass instead of storing them. Less memory, more compute.
Gradient clippingCap the gradient norm to prevent exploding gradients.

Distributed training

  • Data Parallel (DDP) — a full model copy on each GPU, different data shards, gradients averaged. Simple, but limited by the model fitting on one GPU.
  • Tensor / model parallel — split individual layers across GPUs.
  • Pipeline parallel — different layers on different GPUs, micro-batches flowing through.
  • FSDP — shards parameters, gradients and optimizer states across GPUs. PyTorch-native, the common modern choice.
  • DeepSpeed — Microsoft's library. ZeRO stages progressively shard optimizer states (1), gradients (2) and parameters (3), plus offload to CPU or NVMe.
06

Quantization & inference optimization

Why it matters: an FP16 7B model needs roughly 14GB. At 4-bit, roughly 3.5GB. Smaller, faster, cheaper — at some accuracy cost.

Quantization formats

  • GGUF — llama.cpp's format; CPU and Apple-silicon friendly, dominant in local deployment.
  • GPTQ — post-training, layer-wise, GPU-focused, 4-bit.
  • AWQ — activation-aware weight quantization; protects the salient weights identified via activations, often better quality than GPTQ at 4-bit.
  • INT8 / INT4 — the bit widths themselves.
  • PTQ vs QAT — post-training quantization versus quantization-aware training. QAT gives better quality but requires retraining.

Inference optimization

  • KV cache — during generation, keys and values for previous tokens are cached so each new token doesn't recompute the whole sequence. Turns O(n²) per token into O(n). Usually the dominant memory cost at inference.
  • PagedAttention (vLLM) — manages the KV cache in pages like OS virtual memory, dramatically reducing fragmentation and waste.
  • MQA / GQA — Multi-Query and Grouped-Query Attention share K/V heads to shrink the cache. Llama uses GQA.
  • Continuous batching — new requests join the batch as others finish, instead of waiting for a full batch.
  • Speculative decoding — a small draft model proposes tokens, the large model verifies them in parallel.
  • FlashAttention — IO-aware exact attention; faster and lower memory without approximating.
  • Prefix caching — reuse computation for shared prompt prefixes across requests.

07

RAG — retrieval-augmented generation

Documents → Chunking → Embedding → Vector store
                                        ↓
User query → Embed → Similarity search (top-k) → [Rerank] → Prompt → LLM → Answer

Document parsing

PDFs, DOCX and HTML into clean text. The hard parts are tables, multi-column layouts, scanned pages needing OCR, and headers or footers polluting chunks. Tools: unstructured.io, PyMuPDF, LlamaParse. Garbage parsing gives garbage retrieval, and no amount of model quality recovers it.

Chunking strategies

  • Fixed-size with overlap — simple baseline, e.g. 512 tokens with 50 overlap. Overlap stops ideas being cut in half at boundaries.
  • Recursive character — split on paragraph, then sentence, then word boundaries in order.
  • Semantic chunking — split where embedding similarity drops, i.e. at topic changes.
  • Structure-aware — split by heading or section. Usually best when the document has real structure.
  • Parent-document / small-to-big — embed small chunks for precise retrieval, return the larger parent for context.

The trade-off: small chunks retrieve precisely but lose surrounding context; large chunks preserve context but retrieve noisily. Chunking quality determines RAG quality more than model choice does.

Embeddings & vector search

Text becomes a vector so semantic similarity becomes geometric distance. Common models: all-MiniLM-L6-v2 (fast, 384-dim), BGE, E5, OpenAI text-embedding-3. The same model must embed both documents and queries.

  • Exact kNN is O(n) — too slow at scale, so production uses approximate search (ANN).
  • HNSW — layered proximity graph, greedy search from the top layer down. Fast, high recall, memory-hungry. The common default.
  • IVF — cluster the vectors, search only the nearest nprobe clusters. Lower memory; recall depends on nprobe.
  • IVF-PQ — adds Product Quantization to compress vectors. Large memory savings, some accuracy cost.
  • Metrics — cosine similarity, dot product, L2 distance.

Reranking — the two-stage pattern

Bi-encoder (stage 1)

Embeds query and document separately. Fast and precomputable, so it scales to millions of documents. Used for broad recall.

Cross-encoder (stage 2)

Processes query and document together. Far more accurate, far too slow to run over a whole corpus. Used for precision on a shortlist.

Why two stages

Retrieve broadly with the bi-encoder — typically a few hundred candidates — then rerank that shortlist with the cross-encoder. You get most of the cross-encoder's accuracy at a fraction of its cost. This is the standard production retrieval architecture.

Beyond the basics

  • Hybrid search — dense semantic search plus sparse keyword search (BM25). BM25 catches exact terms, product codes, error strings and rare names that embeddings blur. Merge results with Reciprocal Rank Fusion.
  • Query transformation — rewriting for clarity, multi-query paraphrases retrieved in parallel, or decomposition of a complex question into sub-questions.
  • HyDE — ask the LLM to write a hypothetical answer, embed that, and search with it. Works because a hypothetical answer sits closer in embedding space to real answers than the question does.
  • Context integration — ordering matters, since models attend more to the start and end of context: the "lost in the middle" problem. Also deduplication, token budgeting and context compression.
  • Multi-hop reasoning — chained retrieval for questions requiring intermediate facts. Requires retrieve → reason → retrieve again.
  • Citation generation — tie each claim to a source ID so answers are auditable, and so hallucinated justifications become detectable.

RAG evaluation

MetricQuestion it answers
FaithfulnessIs the answer actually supported by the retrieved context? The hallucination check.
Answer relevanceDoes the answer address the question asked?
Context precisionAre the retrieved chunks relevant, or is the context padded with noise?
Context recallDid retrieval find everything needed to answer?
Hit rate, MRR, NDCG@kStandard retrieval ranking quality.
The insight that saves the most time

Evaluate retrieval and generation separately. Most RAG failures are retrieval failures — the model answered badly because the right chunk was never in the context. Debugging the prompt when the problem is the retriever wastes weeks.

CRUD in a vector store

Upsert (insert-or-update by ID), fetch by ID, delete, and filtered search — vector similarity combined with a metadata condition such as tenant_id = "acme". Note that updating a document's text means re-embedding it; the vector isn't editable in place.

Indexing & query optimization

  • Index type — HNSW for recall and speed, IVF for lower memory
  • HNSW parameters — M (graph connectivity), ef_construction (build quality), ef_search (query-time recall vs latency)
  • IVF — nprobe controls how many clusters are searched
  • Quantization for memory savings at some recall cost
  • Sharding and replication for scale and availability
  • Pre- vs post-filtering — filtering before the ANN search preserves result counts but is slower; filtering after is faster but can return too few results. This choice has real performance consequences at scale.
09

Agentic AI

What makes something an agent

An LLM that can decide and act, not just answer. Five components:

  1. Perception — takes input across modalities
  2. Reasoning and routing — decides what to do next
  3. Tool use — calls external functions, APIs and retrieval
  4. Memory — carries state across turns and sessions
  5. Autonomy — acts on triggers without being prompted each time

The agent loop

Observe → Think (which tool?) → Act (call tool) → Observe result → repeat → Answer

Function / tool calling — the mechanism

1. You send tool JSON schemas alongside the request
2. Model returns a structured tool_call — name + arguments
3. Your code executes it — the model never runs anything itself
4. You return the result as a tool message
5. Model continues, or calls another tool

Modern APIs support parallel tool calls, where the model requests several independent tools in one turn. The tool's description is what the model uses to decide — writing precise tool descriptions is genuine engineering work, not documentation.

Patterns

  • ReAct (Reason + Act) — interleaved Thought → Action → Observation cycles. The foundational agent pattern.
  • Router / dispatcher — a classifier picks the right handler or tool before any expensive work happens.
  • Plan-and-Execute — produce a full plan up front, then execute steps. Fewer model calls, less adaptive.
  • ReWOO — plan without interleaved observations to reduce token cost.
  • Reflexion — the agent critiques its own output and retries.
  • Tree of Thoughts — explore multiple reasoning branches and select the best.
  • Supervisor / worker — a coordinating agent delegates to specialists.
  • Human-in-the-loop — pause for approval before consequential or irreversible actions.

The engineering disciplines

Harness engineering

The scaffolding around the model: how context is fed, tools exposed, outputs parsed, retries handled and limits enforced. The harness often matters more than the model.

Loop engineering

Stopping conditions, maximum iterations, detecting repeat loops where the agent cycles on the same action, and knowing when to give up and escalate.

Context engineering

What goes in the window and in what order. Budgeting tokens across system prompt, tool schemas, memory, retrieved documents and history — with compaction when it overflows. Currently the highest-leverage skill in agent building.

Tool design

A small set of well-named tools with precise descriptions and strict schemas beats many overlapping ones. Return errors the model can act on. Make tools idempotent where possible.

Memory architecture

Short-term (conversation window), long-term (vector store), episodic (what happened), semantic (facts), procedural (how to do things). Decide what to write, when to retrieve and when to forget.

Guardrails & permissions

Input validation, output filtering, tool allow-lists, scoped credentials, spend and rate caps, sandboxed execution, approval gates on destructive actions.

Observability & tracing

Spans per LLM and tool call, token and cost accounting, latency breakdown, failure clustering. LangSmith, Langfuse, OpenTelemetry, Arize Phoenix.

Multi-agent frameworks

CrewAI (role-based crews), AutoGen (conversational multi-agent), Google ADK, LangGraph (graph-based, most control), OpenAI Agents SDK.

Evaluating agents

Harder than evaluating a single model response, because the path matters as much as the answer.

  • Task success rate — did it achieve the goal end to end
  • Tool-call accuracy — right tool, right arguments, right order
  • Trajectory evaluation — was the path sensible, or did it stumble into the right answer
  • LLM-as-judge — a model scores outputs against a rubric; cheap, scalable, needs its own validation
  • Latency and cost per task — an agent that succeeds after 40 tool calls may still be unusable
  • Regression suite — a fixed set of cases run on every prompt or model change
The common failure

Teams ship agents with no evaluation harness, then change a prompt and have no way to know whether they improved anything. Build the eval set before the agent gets complicated — retrofitting it is far more painful.

MCP — Model Context Protocol

An open standard for connecting AI models to external tools and data, so integrations aren't rewritten for every client. Often described as "a USB-C port for AI tools." It passes JSON-RPC messages between an MCP client (the AI application) and an MCP server (the thing exposing capabilities).

The three primitives

Tools

Callable functions the model can invoke. The most used primitive by a wide margin.

Resources

Data the model can read.

Prompts

Reusable prompt templates the server offers.

The 2026-07-28 revision

Shipped 28 July 2026, the largest change since launch. Most material written before that date describes the older stateful model.

Previous · 2025-11-25Current · 2026-07-28
Core modelStatefulStateless
Handshakeinitialize / initialized requiredRemoved
SessionsMcp-Session-Id pinned a client to one server instanceRemoved — any instance can serve any request
DeploymentSticky sessions, shared session store, held-open streamsPlain round-robin load balancer
Long-running workIn the core protocolMoved to the Tasks extension
Extensions—New framework, including MCP Apps for server-rendered UI
AuthOAuth 2.1Hardened, closer to OAuth / OIDC; Dynamic Client Registration deprecated
Deprecated—Roots, Sampling, Logging (SEP-2577)

Transports

  • stdio — the server runs as a local subprocess communicating over stdin/stdout. Simplest option for local tools.
  • Streamable HTTP — a single endpoint using POST and GET with optional SSE streaming. Replaced the older HTTP+SSE transport in the 2025-03-26 revision.

Versions are dates in YYYY-MM-DD form. Tier 1 SDKs are TypeScript, Python, Go and C#, and the stateless migration preserved backward compatibility so existing servers continued working.

Why the stateless change matters

Under the old model, a remote MCP server needed sticky sessions and a shared session store because the handshake bound a client to one instance. Removing session state means MCP servers scale like ordinary stateless web services — which is what made remote MCP practical to operate at scale.

LangChain & LangGraph

LangChain core

  • Chains — compose steps into a pipeline. Modern LangChain uses LCEL with the pipe operator: prompt | model | parser, which provides streaming, batching and async for free.
  • Prompts & templates — PromptTemplate and ChatPromptTemplate with variable interpolation, plus few-shot templates with example selectors.
  • Tools & tool calling — a tool is a name, description, input schema and function. The @tool decorator defines one; bind_tools() attaches them to a model.
  • Agents — an LLM in a loop choosing tools until done. The classic AgentExecutor is largely superseded by LangGraph.
  • Memory — conversation buffer, windowed buffer (last k turns), summary memory (LLM-compressed history), vector-backed memory (retrieve relevant past turns).
  • Retrievers — the interface over a vector store: MultiQuery, ContextualCompression, ParentDocument, SelfQuery (the LLM writes metadata filters), EnsembleRetriever for hybrid.
  • Output parsers — enforce structure with PydanticOutputParser or JSON mode, with retry on parse failure.
  • Loaders & splitters — the ingestion side; RecursiveCharacterTextSplitter is the workhorse.
  • Callbacks / LangSmith — tracing, debugging, evaluation and monitoring.

LangGraph

Agents modelled as a stateful graph rather than a linear chain. This is where most serious agent work happens now.

  • State — a typed shared object every node reads and writes, with reducers defining how updates merge (for example appending to a message list rather than overwriting it).
  • Nodes — functions taking state and returning a state update.
  • Edges — transitions between nodes. Conditional edges branch on state, which is how routing is implemented.
  • Cycles — unlike chains, graphs can loop. That is what makes genuine agent loops possible.
  • Checkpointers — persist state at each step, giving durability, time-travel debugging and resumability after a crash.
  • Human-in-the-loop — interrupt() pauses the graph pending approval, then resumes from the checkpoint.
  • Subgraphs & multi-agent — supervisor patterns where a router delegates to specialist subgraphs, or swarm-style handoffs.
  • Streaming — stream both tokens and intermediate state updates to the client.
Choosing an orchestration layer

Visual tools like n8n or Flowise ship fastest and include scheduling and integrations, but logic lives in JSON that is hard to version, review and unit-test. Code-first frameworks like LangGraph put that logic in versioned, testable source. The usual trajectory is prototype visually, then move to code once the workflow matters.

LLM & agent system design

Most LLM systems fail in production for reasons that have nothing to do with model quality. They're too slow, too expensive, silently wrong, or they break the first time a dependency has a bad day. This section is about the parts that decide whether a system survives contact with real traffic.

Where the time actually goes

Before optimising anything, know which stage dominates. In a typical RAG or agent request:

StageTypical shareWhat drives it
Embedding the querySmallModel size; usually milliseconds
Vector searchSmall–mediumIndex type, ef_search / nprobe, corpus size, filtering strategy
RerankingMediumCross-encoder is O(shortlist size) — reranking 500 costs far more than 50
LLM generationUsually dominantOutput tokens × per-token latency. Input length affects time-to-first-token, output length affects total.
Tool calls (agents)Often dominantEach loop iteration is a full round-trip. Ten sequential tool calls means ten LLM calls plus ten API latencies.
The rule

Generation is usually the bottleneck in RAG; the number of sequential loop iterations is usually the bottleneck in agents. Optimising vector search when the LLM is 90% of latency is wasted effort — measure first.

Two latency numbers that matter

  • TTFT — time to first token. Driven by prompt length (the prefill pass) plus queueing. This is what determines whether an interface feels responsive.
  • TPOT — time per output token. Driven by model size, hardware and batch pressure. Total generation time ≈ TTFT + (output tokens × TPOT).

Streaming doesn't reduce total latency, but it collapses perceived latency to TTFT. For any user-facing surface, streaming is the single highest-return change.

Reducing latency

Cut output tokens

The most direct lever, since generation is linear in output length. Ask for concise output, cap max_tokens, avoid making the model restate the input.

Cut input tokens

Shorter prompts reduce prefill time and cost. Trim boilerplate system prompts, retrieve fewer chunks, compress context.

Stream

Send tokens as they generate. Perceived latency drops to TTFT even though total time is unchanged.

Parallelise

Independent retrieval calls, tool calls and sub-questions should run concurrently, not sequentially. Async I/O matters here more than raw compute.

Cache

Exact-match cache for repeated queries; semantic cache keyed on embedding similarity; prompt-prefix caching for shared system prompts. Caching is often a bigger win than any model change.

Route by difficulty

Send easy requests to a small fast model and escalate only hard ones. A classifier or heuristic router in front of the stack cuts both latency and cost substantially.

Shrink the loop

For agents, fewer sequential iterations beats faster iterations. Better tool design and clearer instructions reduce round-trips more than a faster model does.

Speculative decoding

A small draft model proposes tokens that the large model verifies in parallel. Server-side, but worth knowing when evaluating inference providers.

Quality trade-offs

Nearly every optimisation trades against quality. Knowing the exchange rate is the job.

DecisionYou gainYou lose

Make the trade explicit

The mature version of this discussion is not "which is better" but "what are we optimising for, and what is the acceptable floor on the other axis." Define the quality floor as a measurable threshold on an eval set, then optimise cost and latency underneath it.

Handling failure

LLM systems have more failure modes than typical services, because dependencies are slow, rate-limited, non-deterministic and occasionally confidently wrong.

Transport-level failures

  • Timeouts — always set them. An LLM call without a timeout can hang a worker indefinitely.
  • Retries with exponential backoff and jitter — on 429 and 5xx. Jitter prevents thundering-herd retries from synchronising.
  • Idempotency — retrying must not double-charge, double-send or duplicate writes. Use idempotency keys on any action with side effects.
  • Circuit breakers — after repeated failures, stop calling the dependency and fail fast rather than queueing requests behind a dead service.
  • Fallback models — a secondary provider or smaller model when the primary is unavailable. Requires prompt compatibility to be tested in advance.
  • Dead-letter queues — failed work goes somewhere inspectable, never silently dropped.
  • Graceful degradation — return partial results, cached results, or a clear error rather than nothing.

Model-level failures

  • Malformed output — the model returns unparseable JSON. Mitigate with structured output modes, schema validation, and a repair retry that feeds the parse error back.
  • Hallucination — mitigate with retrieval grounding, citation requirements, validation against a source of truth, and permitting "I don't know" as an acceptable answer.
  • Wrong tool, wrong arguments — validate arguments before execution; return actionable errors the model can correct from.
  • Infinite loops — cap iterations, detect repeated identical actions, and escalate to a human or a fallback path.
  • Prompt injection — untrusted content in the context can carry instructions. Treat retrieved documents and tool output as data, never as instructions; scope tool permissions tightly.
  • Silent quality regression — a provider updates a model and behaviour shifts. This is why a pinned regression suite matters more than in conventional software.

Cost control

  • Token cost scales with input and output; long system prompts multiplied by high traffic dominate bills quietly.
  • Model routing — small model by default, large model on escalation, is typically the largest single saving.
  • Caching — exact and semantic; prompt-prefix caching where the provider supports it.
  • Batching — for offline and bulk workloads, batch endpoints are substantially cheaper.
  • Cap agent loops — an unbounded agent is an unbounded invoice.
  • Track cost per request as a first-class metric, alongside latency and error rate.

Scaling

  • Stateless application servers — keep session state in a store, not in process memory, so instances scale horizontally.
  • Queue long work — anything beyond a few seconds belongs in a background job with a status endpoint, not a held-open HTTP request.
  • Continuous batching at the inference layer — this is why vLLM-style servers reach far higher throughput than naive per-request serving.
  • Rate limiting per tenant — one heavy user should not exhaust shared model quota.
  • Separate read and write paths — index building is a batch workload; retrieval is a latency-sensitive one. Don't couple them.

Observability

Conventional metrics are insufficient because a request can succeed with HTTP 200 and still be completely wrong.

  • Tracing — a span per LLM call, tool call and retrieval, so a slow request can be attributed to a stage.
  • Token and cost accounting per request, per feature, per tenant.
  • Latency percentiles — p50 hides the problem; p95 and p99 are where users live.
  • Quality signals — user feedback, thumbs, regeneration rate, escalation rate, abandonment. Regeneration rate is an underrated proxy for dissatisfaction.
  • Offline evaluation — run the regression suite on every prompt, model or retrieval change, not just on code changes.
  • Log the inputs and outputs (subject to privacy constraints) — without them, failures are unreproducible.

What separates systems that work

Evaluation before scale

A regression set built early makes every later change measurable. Without it, teams tune prompts by vibes and cannot tell improvement from regression.

Deterministic where possible

Use rules, validators and code for anything that doesn't need a model. Reserve the LLM for what genuinely requires language understanding. Deterministic components are testable, fast and free.

Constrain the model's job

Narrow, well-specified tasks with structured output succeed far more reliably than open-ended ones. Decomposition beats a single ambitious prompt.

Design for the failure path

Assume every dependency will be slow, rate-limited or wrong at some point. The happy path is the easy part.

Version everything

Prompts, model IDs, retrieval configs and tool schemas are all production configuration. Pin them; changing a model silently is a production change.

Keep a human path

Escalation to a person for low-confidence or high-stakes cases is a feature, not an admission of failure. It also generates the labelled data that improves the system.

Computer vision & edge deployment

Detection fundamentals

  • YOLO — single-stage detector; one forward pass predicts boxes and classes together. Fast, which is why it dominates edge deployment. Size variants run nano, small, medium, large, extra-large — n being smallest and fastest.
  • Two-stage detectors (Faster R-CNN) propose regions first, then classify. More accurate historically, slower.
  • Fine-tuning a detector — start from COCO-pretrained weights and continue training on a labelled custom dataset. Standard practice; training from scratch is rarely worth it.
  • IoU — Intersection over Union, the overlap between predicted and ground-truth boxes.
  • mAP — mean Average Precision, the standard detection metric. mAP@0.5 uses an IoU threshold of 0.5; mAP@0.5:0.95 averages across thresholds and is stricter.
  • NMS — non-max suppression removes duplicate overlapping boxes for the same object.
  • Confidence threshold — trades precision against recall directly, and is often the fastest quality lever available post-training.

Precision, recall and hard negatives

  • Precision — of what the model flagged, how much was correct. Low precision means false alarms.
  • Recall — of what existed, how much was found. Low recall means misses.
  • Hard negatives — visually similar non-targets deliberately added to training data so the model learns the boundary. The standard fix for a specific recurring false positive.
  • Class imbalance — rare classes get under-predicted; handled with resampling, loss weighting or focal loss.
Small-object detection

Distant or small objects are the hardest case: at long range a target may occupy only a handful of pixels, leaving very little signal. Standard approaches are higher input resolution, tiled inference over image patches, targeted data collection at that scale, anchor tuning, and using temporal information across frames — motion patterns often separate classes that single frames cannot.

Augmentation

Synthetic variation so the model generalises beyond the training distribution: horizontal flip, scale and crop, rotation, HSV and brightness shifts for lighting conditions, blur and noise, and mosaic (combining four images) which is standard in the YOLO training pipeline. Augmentation choice should mirror the conditions the model will actually face — night, weather, angle, distance.

Edge deployment

  • The constraint set — accuracy, latency, memory and power all bind simultaneously. Edge work is largely about managing that four-way trade-off.
  • ONNX — an interchange format for moving models between frameworks and runtimes.
  • TensorRT — NVIDIA's inference optimiser; layer fusion, precision calibration, kernel tuning. Substantial speedups on Jetson-class hardware.
  • Quantization — INT8 post-training quantization is the standard edge win; the model shrinks and speeds up with a modest accuracy cost.
  • Pruning — remove low-importance weights or channels.
  • Model size selection — choosing a nano over a large variant is usually a bigger practical win than any post-training optimisation.
  • Pipeline cost — capture, decode, preprocess and post-process often consume more time than inference itself. Profile the whole pipeline, not just the model.

Python & APIs

  • FastAPI vs Flask — FastAPI is async-native (ASGI), auto-generates OpenAPI/Swagger documentation, and validates with Pydantic. Flask is sync (WSGI), lighter and more manual. For LLM workloads, async matters because handlers spend most of their time waiting on network calls.
  • Pydantic — type-validated data models; FastAPI uses it to validate requests and responses automatically.
  • async / await — non-blocking I/O lets one worker handle many concurrent requests while waiting. Critical when every request calls a slow model API.
  • REST verbs — GET, POST, PUT/PATCH, DELETE. Status codes: 200, 201, 400, 401, 404, 429 rate limited, 500, 503.
  • WebSockets vs SSE vs REST — REST for request/response; SSE for one-way server streaming (the common choice for token streaming); WebSockets for genuine bidirectional communication.
  • Idempotency — the same request applied twice produces the same result. Essential wherever retries exist.
  • Backpressure — when downstream is slower than incoming traffic, queue with limits and shed load deliberately rather than collapsing.
  • Docker — package application and dependencies into a portable image; the standard unit of deployment.
  • CI/CD — automated test, build and deploy on every commit.

Quick reference

RAG or fine-tuning?RAG changes available knowledge at runtime; fine-tuning changes behaviour. Facts and freshness → RAG. Style, format, domain tone → fine-tune.
Why rerank after retrieving?Bi-encoders are fast and precomputable for millions of documents; cross-encoders are accurate but slow. Retrieve broad, rerank narrow.
How do you prevent hallucination?Ground in retrieved context, require citations, force structured output, validate before returning, keep temperature low, allow "I don't know".
Agent vs chatbot?An agent decides and acts — tool selection, memory, autonomous triggers. A chatbot only responds.
What dominates latency?Generation in RAG systems; number of sequential loop iterations in agents. Measure before optimising.
How do you handle an API failure?Timeouts, exponential backoff with jitter, circuit breaker, fallback model, dead-letter queue, graceful degradation.
How do you reduce cost?Route easy requests to a small model, cache aggressively, trim prompts, batch offline work, cap agent iterations.
How do you choose a model?Task fit, latency budget, cost per token, context window, and whether it must run on-premise or at the edge.
Which vector database?FAISS for local and embedded, pgvector if Postgres is already there, Qdrant/Weaviate/Pinecone for managed scale with filtering.
What's a token?Roughly four characters. Everything is billed and limited by them.
How do you test an agent?Fixed regression suite, task success rate, tool-call accuracy, trajectory review, LLM-as-judge, latency and cost tracking.
