01

Context length is not built from n-grams

Correcting a misconception

You asked how context length is built using n-grams and bigrams. It isn't. Those are the pre-2017 statistical approach that transformers replaced. Saying it in the room would signal a gap in fundamentals — so here's the real answer.

N-grams — the old way

An n-gram model predicts the next word using only the previous n−1 words, by counting frequencies in a corpus.

  • Bigram (n=2): P(next | 1 previous word). "New" → "York" is frequent, so predict "York."
  • Trigram (n=3): P(next | 2 previous words).

Three fatal flaws

  1. Fixed, tiny window. A 5-gram sees 4 words. It cannot connect "the drone" at the start of a paragraph to "it" at the end.
  2. Combinatorial explosion. A 50,000-word vocabulary gives 50,000³ = 125 trillion possible trigrams. Most never occur — the sparsity problem — forcing hacks like smoothing and backoff.
  3. No notion of meaning. "cat" and "kitten" are unrelated symbols with no shared representation.

Transformers — how it actually works

Context length comes from self-attention, not counting.

  • Every token becomes an embedding — a dense vector carrying meaning.
  • Self-attention lets every token look at every other token in the window at once, learning how much to weight each. Token 4,000 can attend directly to token 1.
  • Context length = how many tokens can be attended over simultaneously. Bounded by architecture and compute, not by an n-gram order.
  • The real limit is cost: attention is O(n²). Double the context, quadruple compute and memory. That is the entire reason long context is expensive.
  • Positional encoding supplies order, since attention alone is order-blind. Modern models use RoPE, which also enables context extension beyond the trained length.
Say it like this

"Context length comes from self-attention — every token attends to every other token in the window, so there's no fixed n-word lookback like an n-gram model. The constraint is that attention scales quadratically with sequence length, which is why long context is expensive. N-grams were the older statistical approach with a fixed tiny window and severe sparsity problems; transformers replaced them precisely because attention handles long-range dependencies."

If they ask about n-grams directly, they're testing NLP history. Say they were the pre-neural approach, name the sparsity and fixed-window problems, and note transformers solved both.

MCP — and the change from three weeks ago

In their required skills · recently changed

The 2026-07-28 specification shipped on 28 July 2026 — the largest revision since launch. Most candidates will describe the old stateful model. Describing the new one puts you ahead of people with years more experience.

What it is, in one sentence

An open standard for connecting AI models to external tools and data, so you don't write bespoke glue for every integration — often called "a USB-C port for AI tools." It passes JSON-RPC messages between an MCP client (your AI app) and an MCP server (the thing exposing tools and data).

The three primitives

Tools

Callable functions the model can invoke. This is the one that matters most.

Resources

Data the model can read.

Prompts

Reusable prompt templates.

Transports (both versions)

  • stdio — server runs as a local subprocess over stdin/stdout. Simplest for local tools.
  • Streamable HTTP — single endpoint, POST/GET, optional SSE streaming. Replaced the older HTTP+SSE transport in the 2025-03-26 revision.

Versioning uses dates: YYYY-MM-DD. Tier 1 SDKs are TypeScript, Python, Go and C#, and all preserved backward compatibility — existing servers didn't break.

Say it like this

"I haven't used MCP in production yet. My understanding is it's the open standard for connecting models to external tools and data — JSON-RPC between a client and server, exposing tools, resources and prompts.

The notable thing is it just went through its biggest revision, the 2026-07-28 spec, which made the protocol stateless — they removed the initialize handshake and the session header, so a remote MCP server can now sit behind an ordinary load balancer instead of needing sticky sessions. Long-running work moved into a Tasks extension.

Conceptually it solves the same problem my decision-LLM router solves in JARVIS — deciding which tool to call and calling it — but standardised, so any client can talk to any server."

Agentic AI — the job title

What makes something an agent

An LLM that can decide and act, not just answer. Five parts:

  1. Perception — takes input (text, voice, image, documents)
  2. Reasoning / routing — decides what to do
  3. Tool use — calls external functions, APIs, retrieval
  4. Memory — carries state across turns
  5. Autonomy — acts without being prompted each time
Your work

JARVIS has all five. Say that explicitly. Router + decision LLM (2,3), Whisper/vision/document handlers (1,3), five Notion databases (4), cron-triggered workflows and the 5-minute reminder check (5).

The agent loop

Observe → Think (which tool?) → Act (call tool) → Observe result → repeat → Answer

Patterns to know by name

  • ReAct (Reason + Act) — interleaved Thought → Action → Observation cycles. The foundational pattern.
  • Function / tool calling — you pass tool JSON schemas → the model returns a structured tool_call with name and arguments → your code executes it (the model never runs anything) → you return the result as a tool message → the model continues. Modern APIs support parallel tool calls.
  • Router pattern — a classifier picks the right handler. Exactly what your Message Router and Decision LLM do.
  • Planning — Plan-and-Execute (full plan, then run), ReWOO (plan without observations to save calls), Reflexion (self-critique and retry), Tree of Thoughts (explore branches).
  • Multi-agent — CrewAI (role-based crews), AutoGen (Microsoft, conversational), Google ADK (you hold this certification — mention it), LangGraph (graph-based, most control), OpenAI Agents SDK.
  • Human-in-the-loop — pause for approval before a consequential action.

The engineering disciplines

Harness engineering

The scaffolding around the model: feeding context, exposing tools, parsing outputs, retries, limits. The harness often matters more than the model.

Loop engineering

Stopping conditions, max iterations, detecting repeat loops, knowing when to give up and escalate.

Context engineering

What goes in the window and in what order. Budgeting tokens across system prompt, tools, memory, retrieved docs and history. Currently the highest-leverage skill in agent building.

Tool design

Few well-named tools with precise descriptions and strict schemas beat many overlapping ones. Return errors the model can act on.

Memory architecture

Short-term (window), long-term (vector store), episodic (what happened), semantic (facts), procedural (how to). Decide what to write, when to retrieve, when to forget.

Guardrails & permissions

Input validation, output filtering, tool allow-lists, scoped credentials, spend caps, sandboxing, approval gates.

Observability & tracing

Spans per LLM and tool call, token and cost accounting, latency breakdown, failure clustering. LangSmith, Langfuse, OpenTelemetry, Arize Phoenix.

Orchestration patterns

Single agent + tools; router/dispatcher; supervisor + workers; sequential pipeline; parallel fan-out then aggregate; reflection.

Evaluating agents

A common question, and most candidates fumble it. Answer in layers:

  • Task success rate — did it achieve the goal end to end
  • Tool-call accuracy — right tool, right arguments
  • Trajectory evaluation — was the path sensible, not just the final answer
  • LLM-as-judge — a model scores outputs against a rubric
  • Latency and cost per task — production reality
  • Regression suite — fixed test cases run on every change
Your answer

"In my BTC OpenEnv project I built exactly this — a grading system with dense reward shaping and fully seeded, reproducible scoring, then benchmarked three agents against identical graded tasks. That's agent evaluation, in an RL framing."

Observability is the gap in JARVIS. No tracing, no alerting, no cost dashboards. Say so before they find it: "That's the layer I'd add first in a real deployment."

RAG — you've built most of this

Documents → Chunking → Embedding → Vector store
                                        ↓
User query → Embed → Similarity search (top-k) → [Rerank] → Prompt → LLM → Answer

Document parsing

PDFs, DOCX and HTML into clean text. The hard parts are tables, multi-column layouts, scanned pages needing OCR, and headers/footers. Tools: unstructured.io, PyMuPDF, LlamaParse. Garbage parsing gives garbage RAG.

Chunking strategies

  • Fixed-size + overlap — simple baseline (e.g. 512 tokens, 50 overlap). Overlap stops ideas being cut in half.
  • Recursive character — split on paragraph → sentence → word boundaries in order.
  • Semantic chunking — split where embedding similarity drops, i.e. at topic changes.
  • Structure-aware — split by heading or section. Usually best when structure exists.
  • Parent-document / small-to-big — embed small chunks for precise retrieval, return the larger parent for context.

The trade-off: small chunks give precise retrieval but lose context; large chunks keep context but retrieve noisily. Chunking quality determines RAG quality more than model choice.

Embeddings and vector search

Text becomes a vector so semantic similarity becomes distance. Models: all-MiniLM-L6-v2 (fast, 384-dim, yours), BGE, E5, OpenAI text-embedding-3. The same model must embed both documents and queries.

  • Exact kNN is O(n) — too slow at scale, so we approximate (ANN).
  • HNSW — layered proximity graph, greedy search from the top layer down. Fast, high recall, memory-hungry. The common default.
  • IVF — cluster the vectors, search only the nearest nprobe clusters. Lower memory; recall depends on nprobe.
  • IVF-PQ — adds Product Quantization to compress vectors. Big memory savings, some accuracy cost.
  • Metrics — cosine similarity, dot product, L2.

Reranking — your architecture

Bi-encoder

Embeds query and document separately. Fast, precomputable, scales to millions.

Cross-encoder

Processes query and document together. Far more accurate, far too slow for 100,000 docs.

Your work

This is exactly why you retrieve 500 then rerank. Say it in those terms — broad recall from the bi-encoder, precision from the cross-encoder. Your reranker (ms-marco-MiniLM) is an encoder model, which is why it reads query and document bidirectionally and scores better.

Beyond the basics

  • Hybrid search — dense semantic + sparse keyword (BM25). BM25 catches exact terms, product codes and rare names that embeddings blur. Merge with Reciprocal Rank Fusion.
  • Query transformation — rewriting, multi-query paraphrases, or decomposition into sub-questions.
  • HyDE — ask the LLM to write a hypothetical answer, embed that, and search with it. Works because a fake answer sits closer in embedding space to real answers than the question does. Good one to name-drop.
  • Context integration — ordering matters; models attend more to the start and end, the "lost in the middle" problem. Also deduplication, token budgeting, compression.
  • Multi-hop reasoning — chained retrieval for questions like "who directed the film that won X?" Requires retrieve → reason → retrieve again.
  • Citation generation — tie every claim to a source. Your attribute-grounded reasoning strings are this idea.

Fine-tuning & LLM training

Where fine-tuning fits

Prompting (change instructions) → RAG (change available knowledge) → Fine-tuning (change the weights).

Rule of thumb: RAG for facts, fine-tuning for behaviour, format and domain style.

SFT and PEFT

SFT — Supervised Fine-Tuning: train on labelled input → output pairs. The standard first step for adapting a base model to a task or instruction format.

PEFT — Parameter-Efficient Fine-Tuning: full fine-tuning of a 70B model needs enormous GPU memory, so PEFT freezes most weights and trains a small number of new parameters.

LoRA — the dominant method

Freeze weight matrix W; learn two small matrices A and B where ΔW ≈ B·A, with rank r far smaller than full dimension. Trains ~0.1–1% of parameters.

  • r — rank / capacity (8, 16, 32, 64)
  • alpha — scaling
  • Target modules — usually attention Q/K/V/O

Adapters are a few MB, so you can swap many onto one base model — and merge them at inference for zero added latency.

QLoRA

LoRA on a 4-bit quantized base. Makes fine-tuning large models possible on a single consumer GPU. Introduced NF4, double quantization, paged optimizers.

Adapters

Small bottleneck layers between transformer layers. Predates LoRA; adds inference latency because it can't be merged.

Prefix & Prompt Tuning

Prefix: trainable vectors prepended to keys/values at every layer. Prompt: lighter still — soft prompt embeddings at the input only. Works well only at large scale.

BitFit

Train only the bias terms. Extremely few parameters, surprisingly decent on some tasks.

Side Tuning

Train a separate small side network whose output combines with the frozen base.

If asked "which would you use?"

"LoRA or QLoRA in almost every case. They're the practical standard — good quality, tiny adapters, mergeable at inference. The others are mostly historical or research interest now."

Preference alignment

  • RLHF — train a reward model on human preference comparisons, then optimise the LLM against it with RL (PPO). Powerful, complex, unstable.
  • DPO — skips the reward model and the RL loop entirely; optimises directly on preference pairs with a classification-style loss. Simpler, more stable, now widely preferred.
  • Also: KTO, ORPO, RLAIF (AI feedback instead of human).

Tokenization & dataset preparation

  • BPE — start from characters, iteratively merge the most frequent pairs. Used by GPT.
  • WordPiece (BERT), SentencePiece / Unigram (language-agnostic, no pre-tokenization).
  • Why subwords? Handles unseen words, keeps vocabulary manageable, works across languages.
  • Dataset prep: deduplicate, quality-filter, format into the chat template, mask prompt tokens so loss is computed only on the response, handle truncation, hold out a validation split.
Your work

You did the CV equivalent on the Army project — the Roboflow data was mislabelled and you corrected and re-labelled it before training. Say that. Data quality work is respected far more than people expect.

Training mechanics

TermWhat it does
Mixed precision (AMP)Compute in FP16/BF16 for speed and memory, keeping an FP32 master copy. BF16 has wider range and is more stable. Uses loss scaling so small gradients don't underflow.
Gradient accumulationCan't fit batch 32? Run 8 micro-batches of 4, accumulate, step once. Simulates a large batch on small hardware.
LR schedulingWarmup (start tiny, ramp up — prevents early instability) then decay (cosine or linear). Nearly all LLM training uses warmup + cosine.
Weight decayL2-style regularisation shrinking weights toward zero. AdamW decouples it from the gradient update — that's the "W".
Gradient checkpointingRecompute activations in the backward pass instead of storing them. Less memory, more compute.
Gradient clippingCap gradient norm to prevent exploding gradients.

Distributed training

  • Data Parallel (DDP) — full model copy per GPU, different data shards, gradients averaged. Simple; limited by the model fitting on one GPU.
  • Tensor / Model Parallel — split individual layers across GPUs.
  • Pipeline Parallel — different layers on different GPUs, micro-batches flowing through.
  • FSDP — shards parameters, gradients and optimizer states. PyTorch-native, the common modern choice.
  • DeepSpeed — Microsoft library. ZeRO stages progressively shard optimizer states (1), gradients (2), parameters (3), plus offload to CPU/NVMe.
Position this honestly

"I understand these conceptually but haven't run multi-GPU training — my work has been single-GPU fine-tuning and edge deployment. It's an area I'd want to learn on real infrastructure." Do not pretend otherwise. This is the easiest place to get caught.

Quantization & inference optimization

Why: an FP16 7B model needs ~14GB. At 4-bit, ~3.5GB. Smaller, faster, cheaper.

  • GGUF — llama.cpp's format; CPU and Apple-silicon friendly, huge in local deployment.
  • GPTQ — post-training, layer-wise, GPU-focused, 4-bit.
  • AWQ — activation-aware; protects salient weights, often better quality than GPTQ at 4-bit.
  • PTQ vs QAT — post-training quantization vs quantization-aware training (better, needs retraining).
  • KV cache — cache keys and values for previous tokens so each new token doesn't recompute the sequence. Turns O(n²) per token into O(n). Usually the dominant memory cost at inference.
  • PagedAttention (vLLM) — manages the KV cache in pages like OS virtual memory. Far less fragmentation.
  • MQA / GQA — share K/V heads to shrink the cache. Llama uses GQA.
  • Also: continuous batching, speculative decoding, FlashAttention, prefix caching.

Transformers

Self-attention — the core idea

For each token, compute three vectors: Query (Q), Key (K), Value (V).

Query

"What am I looking for?"

Key

"What do I contain?"

Value

"What do I contribute?"

Every token's Q is compared against every token's K to produce attention weights, used to take a weighted sum of the V vectors.

Scaled dot-product attention

Attention(Q,K,V) = softmax( (Q · Kᵀ) / √dk ) · V
  • Q · Kᵀ — similarity between every query and every key
  • Why divide by √dk? With large dimensions the dot products grow, pushing softmax into regions with vanishing gradients. Scaling keeps training stable. Classic interview question — know the "why", not just the formula.
  • softmax — turns scores into weights summing to 1

Multi-head attention

Run attention h times in parallel with different learned projections, then concatenate. Each head specialises — one tracks syntax, another long-range references, another local context. More expressive than one big head.

Positional encoding

Attention is permutation-invariant — without position information, "dog bites man" equals "man bites dog." Fixes:

  • Sinusoidal — fixed sine/cosine patterns (original paper)
  • Learned — trained position embeddings
  • RoPE (Rotary) — rotates Q/K by position; used in Llama, enables context extension. Current standard.
  • ALiBi — biases attention by distance

Masking

  • Causal / look-ahead mask — in decoders, token i only sees tokens ≤ i. This is what makes generation autoregressive and prevents cheating by seeing the future.
  • Padding mask — ignore padding tokens in batched sequences.

The transformer block

x → LayerNorm → Multi-Head Attention → + residual
  → LayerNorm → Feed-Forward Network  → + residual
  • Layer normalization — normalises across features, stabilises training. Pre-LN (norm before the sublayer) is now standard over the original Post-LN. Many modern models use RMSNorm, which is cheaper.
  • Feed-forward network — two linear layers with a non-linearity, applied per position. Usually expands to 4× model dimension and back. Holds most of the model's parameters.
  • Residual connections — the + x skip; lets gradients flow through very deep stacks.

The three architectures

TypeAttentionExamplesBest for
Encoder-onlyBidirectionalBERT, RoBERTa, DistilBERTUnderstanding: classification, NER, embeddings, reranking
Decoder-onlyCausal, left-to-rightGPT, Llama, MistralGeneration. All modern LLMs.
Encoder-decoderBothT5, BARTSeq2seq: translation, summarisation
  • BERT — trained with Masked Language Modelling (predict hidden words) plus next-sentence prediction. Bidirectional.
  • RoBERTa — BERT trained better: more data, longer, no NSP, dynamic masking.
  • DistilBERT — distilled: ~40% smaller, ~60% faster, ~97% of performance.
  • Decoder / Causal LM — trained on next-token prediction. "Autoregressive" means generate one token, append, repeat.
  • T5 — everything framed as text-to-text.

LangChain & LangGraph

Be honest here

You used n8n, not LangChain. Know the concepts, don't claim production use. The mapping between them is your strongest angle — see the closing line below.

LangChain core

  • Chains — compose steps into a pipeline. Modern LangChain uses LCEL with the pipe operator: prompt | model | parser. Gives streaming, batching and async for free.
  • Prompts & templates — PromptTemplate / ChatPromptTemplate with variable interpolation; few-shot templates with example selectors.
  • Tools & tool calling — a tool is name + description + input schema + function. The description is what the LLM uses to decide, so writing good tool descriptions is real engineering. @tool decorator; bind_tools() attaches them.
  • Agents — an LLM in a loop choosing tools until done. The classic AgentExecutor is now largely superseded by LangGraph.
  • Memory — conversation buffer, windowed buffer (last k), summary memory (LLM-compressed), vector-backed memory (retrieve relevant past turns).
  • Retrievers — the interface over a vector store: MultiQuery, ContextualCompression, ParentDocument, SelfQuery (LLM writes metadata filters), EnsembleRetriever (hybrid).
  • Output parsers — enforce structure (PydanticOutputParser, JSON) with retry on parse failure.
  • Loaders & splitters — ingestion; RecursiveCharacterTextSplitter is the workhorse.
  • Callbacks / LangSmith — tracing, debugging, evaluation, monitoring.

LangGraph — the one that matters now

Agents modelled as a stateful graph rather than a linear chain.

  • State — a typed shared object (often a TypedDict) every node reads and writes, with reducers merging updates (e.g. appending to a message list).
  • Nodes — functions taking state and returning a state update.
  • Edges — transitions. Conditional edges branch on state. This is how routing is implemented — the LangGraph equivalent of your Message Router.
  • Cycles — unlike chains, graphs can loop. That's what makes real agent loops (think → act → observe → think) possible.
  • Checkpointers — save state at each step: durability, time-travel debugging, resumability.
  • Human-in-the-loop — interrupt() pauses the graph for approval, then resumes.
  • Subgraphs & multi-agent — supervisor pattern (router agent delegating to specialists) or swarm/handoff patterns.
  • Streaming — stream tokens and intermediate state updates.
Your honest line — this lands well

"I built my orchestration in n8n rather than LangChain — visual workflow, built-in scheduling and integrations, which let me ship it and actually run it 24/7.

The concepts map directly: my Message Router is conditional edges, my Context Loader is state loading, my Notion databases are the persistence layer. For a team codebase I'd move to LangGraph — logic in versioned, testable Python beats JSON workflow definitions."

  • Edge inference — TensorRT, ONNX, quantization to run fast on Jetson.
Framing the bird false-positives

"It's a precision problem — at 1000 metres a bird and a drone are both a few dark pixels, so there's very little signal. The fixes are hard negatives, meaning labelled bird data so the model learns the boundary, and using temporal information, because drones and birds move very differently across frames. Single-frame detection throws that signal away."

Remember

Volunteering a real limitation with a concrete fix is a strength, not a weakness. Most candidates hide flaws. Don't skip this one.

When you don't know something

Use this shape

"I haven't worked with that directly. My understanding is [what you do know]. The way I'd approach it is [concrete first step]. Is that roughly how it's used here?"

That reads as senior, not junior. Never bluff a number, a parameter value, or a tool you haven't touched. Every good interviewer probes one level deeper than your first answer, and invented detail collapses exactly there.

On the augmentations you can't recall

"We used the Ultralytics augmentation pipeline — the standard set around HSV and brightness, scale, flip and mosaic. I'd have to check the exact config; that was over a year ago." Say that. Do not invent parameter values.

On the missing photos

"It was a defence deployment — we weren't permitted to take photos or video, and I can't share specifics beyond what I've described." Completely normal, and they will respect it.
